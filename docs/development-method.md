# Struis 開発手法 仕様(struis-ios)

- 版: 5(2026-11-07)。版4のレビューの指摘を反映した。マージキューを `pull_request_target` で動かす、並び順を毎回 GitHub の状態から計算する、古い緑を pending に戻す、Dev Box を main の定義で起動する、など。
- 対象: `DigiLog-lab/struis-ios` の実装・検証・マージ・報告の回し方
- 状態: Dev Box は事前検証を終え、実装中(#91)。マージキューは未実装(#92、#91 にブロックされる)。実装の前に、末尾の「未検証の前提」を試して確かめる。
- 名前は業界で通じる言葉を使う。独自の GitHub のラベルは使わない。

---

## 1. 目的
- 常駐の Mac が無くても、web 版の Claude が PM として、実装から main へのマージまでを回す。
- Claude は、Mac の上の Claude が手元で `xcodebuild` を使うのと同じ感覚で、CI の macOS ランナーを使って書く・ビルドする・テストする・画面を見る。
- macOS ランナー(同時5台)は、実際に使っている間だけ握る。使っていない時は返す。
- main に入るのは、最新の main と合わせて検証したものだけにする。
- 夜中にどこか1か所が詰まっても、それ以外は朝までに終わらせる。持ち主が夜中に監視しなくてよい。

## 2. 前提
- 常駐の Mac は無い。ビルド・テスト・シミュレータは GitHub Actions の macOS ランナー(`xcode-27`、3コア・7GB)で回す。リポジトリは公開(macOS ランナーを無料で使うため)。
- 持ち主はスマホから指示とレビューをする。設定やサインインなどの手作業は持ち主に回さない。ただし、Claude の環境で止められて代わりが利かないもの(「12. 持ち主の操作」)だけは持ち主に頼む。
- PR はまとめる。新しい PR を作る前に持ち主に相談する。ただし「11. 作業の決まり」の「1つの Issue で変える機能は1つ」で分ける PR は、相談済みとみなす。
- テストは最小限。UI テストの全件は流さない。赤は skip・再試行・判定の緩和で通さず、止めて直す。
- 持ち主が許可した PR はマージしてよい(実際のマージは GitHub の自動マージが行う)。
- main はルールセットで保護する(PR 経由、必須のステータスチェック `Struis / verify`、削除と force push の禁止、マージの方法は `merge` だけ)。GitHub 標準のマージキューは個人のアカウントのリポジトリでは使えないので、マージキューは自前で持つ。

## 3. 役割
| 役 | やること |
|---|---|
| 持ち主 | 指示、判断、PR のマージの許可(自動マージの有効化)、見た目と動きの最終確認 |
| web 版 Claude(PM) | Issue の分解と事前検証、コードを書く、Dev Box でのビルド・テスト・画面の確認、PR、マージキューの監視、日次レポート |
| Dev Box | Claude がコードを書いている間ずっと使う macOS ランナー。Claude のリモート実行の命令をそのまま実行する |
| マージキュー(自前) | 自動マージが有効になった PR を1本ずつ、最新の main の上で検証する。main に入る前の唯一のゲート |
| Issue エージェント | 原則使わない。Dev Box で代わりが利かない時だけ、1回の実行で終わる範囲と時間を区切って指示する |

## 4. 全体の流れ
1. **受ける**: 持ち主の指示を受けたら、作業を段階に分ける。
2. **事前検証(preflight check)**: 全部の段階を試す。使う API を実際に呼び(書き込みは害のない形で)、権限・機能が使えるか、持ち主の手作業が要るかを確かめる。持ち主の判断や操作が要る箇所は、着手の前にまとめて全部伝える。判断は1つずつ聞く。
3. **Dev Box を立てる**: アプリのコードに触る作業なら、最初に Dev Box を立て、Claude がコードを読んでいる間に温めておく。
4. **書く・ビルドする・テストする・画面を見る**: Claude の環境でコードを書いて作業ブランチに push し、リモート実行で Dev Box に `xcodebuild` やシミュレータの命令を出す。
5. **PR**: Issue ごとに PR を1本にまとめる。Dev Box で流したテストとその結果を PR に書く。変えた画面の前後比較のスクショと、動きが変わるなら動画を、持ち主に会話で送る。
6. **許可**: 持ち主が PR で GitHub の「Enable auto-merge」(自動マージ)を押す。GitHub Mobile からも押せる。
7. **マージ**: マージキューが1本ずつ、最新の main の上で検証して `Struis / verify` を書く。緑になった時点で、GitHub の自動マージが、ボタンを押した持ち主の名前でマージする。
8. **監視**: Claude はスケジュール実行で起き、結果を見て次を進める。
9. **日次レポート**: 朝に1回。終わったもの、持ち主の操作が要るもの(何を1つ)。

## 5. Dev Box(Claude のリモート開発環境)
- **いつ立てるか**: アプリのコードに触る作業を始めたら、最初に立てる。
- **起動**: `.github/workflows/devbox.yml` を main の定義のまま `workflow_dispatch` で起動し、入力の作業ブランチを checkout する。作業ブランチの定義で起動すると、そのブランチがジョブの権限を書き換えられるため。
- **立ち上がり**: キャッシュ(ネイティブ依存、作業ブランチまたは main の DerivedData)を戻して1回ビルドし、シミュレータを起動したまま待機する。かかる時間は「14. 見込み」。
- **リモート実行(`mac` コマンド)**: `scripts/devbox/mac.py`。手元の端末と同じ感覚で使う。
  - 例: `mac run -- xcodebuild test-without-building -only-testing:striusTests/UsageGateTests`、`mac run -- 'xcrun simctl io booted screenshot "$DEVBOX_FILES/home.png"'`。
  - 引数が1つならシェルの1行として、2つ以上ならそのままの引数として実行する。
  - 命令を実行する前に、Dev Box は作業ブランチの最新を取り込む。DerivedData は作業ツリーの外に置くので、2回目以降はインクリメンタルビルドになる。
  - 返ってくるもの: ログの末尾(全文は gzip)、終了コード、時刻、命令が `$DEVBOX_FILES` に置いたファイル(手元の `devbox-out/<id>/` に入る)。
  - 長い命令は15秒ごとにログの末尾を返すので、終わる前から進み具合が見える。`mac run --async` で裏で走らせ、`mac wait <id>` で後から結果を取る。
- **やり取りの経路**: 命令は `devbox/cmd` ブランチの1コミット、結果は `devbox/out` ブランチの1コミット(毎回 force push で上書き)。両側とも `git ls-remote` で数秒おきに見る。git の操作は GITHUB_TOKEN の REST の上限(1リポジトリにつき1時間1,000回)に数えられない。3秒おきに REST で見ると1時間1,200回になり、上限を超える。
  - ファイルも Artifact ではなく `devbox/out` で返す。Artifact はステップとしてしか置けず、命令を待つ1つのステップの途中では置けないため。
  - `devbox/*` への push で動くワークフローは無い(どのワークフローも、push で動くのは main だけ)。
- **アイドルタイムアウト**: 命令が15分来なければ、Dev Box は自分で終わる。必要になったら立て直す。`mac stop` ですぐ終わらせることもできる。
- **6時間の上限**: 1本のジョブは6時間で切れるので、近づいたら DerivedData を保存し、次の Dev Box に引き継ぐ。
- **ランナーの割り当て**: Dev Box 1台、マージキューの検証2台、残り2台を Ad Hoc のプロトタイプのビルドやネイティブ依存のキャッシュ作りに回す。
- **ゲートには使わない**: Dev Box で作ったビルドは、マージのゲートには使わない。命令で何でも実行できるので、push したコードと同じものから作られた保証が無いため。Dev Box のジョブには `statuses: write` を持たせない(`Struis / verify` を書けないようにする)。権限は `devbox/out` への push に要る `contents: write` だけ。
- **公開されること**: リポジトリは公開なので、命令と出力は誰でも読める。秘密の値を命令や出力に出さない。Dev Box のジョブには、ビルドとテストに要らない秘密の値を渡さない。

## 6. テストの選び方(テスト影響分析)
- Dev Box でもマージキューでも、流す UI テストは `scripts/ci/ui-test-plan.json` の規則で変更から選ぶ。
- マージキューは、選び方(`ui-test-plan.json`、`ui_test_plan.py`)と UI だけの判定(`cosmetic.py` の `ALLOWED`)を、**main の版**で使う。PR の版を使うと、PR が自分の `ALLOWED` を広げて自分のテストを外せるため。
- 「全件に回す」(`everything`)規則は、本当に全画面に効くものだけにする(`strius/App/**`、`strius/striusApp.swift`、`Info.plist` など)。
- 外すもの:
  - `scripts/ci/ui-test-plan.json`・`scripts/ci/ui_test_plan.py`: 選び方の変更は、選び方の単体テストで確かめる。
  - `strius/Auth/**`: ファイルごとに関係する画面のテストへ割り当てる。
- 検証のワークフロー(`ios.yml` とキュー)の変更は外さない。「7. マージキュー」の「検証のワークフローに触る PR」のとおり、PR の定義で1回流す。
- 試算: 課金の処理を変えた PR(#84)で、48本(約44分)→6本(約3分)。

## 7. マージキュー(自前、main に入る前の唯一のゲート)
- **起動**: `pull_request_target`(`auto_merge_enabled`・`auto_merge_disabled`・`synchronize`・`closed`)、main への `push`、検証の `workflow_run` の完了。`pull_request_target` は main の定義で動く(`pull_request` は PR のマージ用コミットの定義で動くので使わない)。
- **入口**: 持ち主が PR で「Enable auto-merge」を押すと、キューに入る。自動マージを押すことがマージの許可。
  - 合図にレビューの承認(Approve)は使わない。PR の作成者は自分の PR を承認できず、Claude が作る PR は持ち主のアカウント(`DigiLog-lab`)の名前で作られるため。
  - ルールセットが求める承認数は0なので、承認が無くてもマージの妨げにはならない。
  - GitHub は、すぐマージできる PR には「Enable auto-merge」を出さない。だからキュー以外が `Struis / verify` を緑にしてはいけない(緑だとボタンが出ず、キューに入れない)。
  - このリポジトリの PR だけを受ける。フォークからの PR はキューに入れない。
- **状態を持たない**: キューは起動のたびに、GitHub の状態から次にやることを計算する。待ちのファイルもラベルも持たない。
  - キューの中身: 開いていて、main 向けで、自動マージが有効な PR。
  - 並び順: 「自動マージを押した時刻」と「最後の push の時刻」の遅い方が早い順(Issue のタイムラインの `auto_merge_enabled` と、先頭のコミットの push の時刻)。赤を直して push した PR は、これで自然に最後に並ぶ。
  - Issue に GitHub の依存関係(Blocked by)があり、ブロックしている Issue が閉じていない PR は飛ばし、次の PR を見る。先頭で止めない。
  - 同時実行の制御(concurrency)は `queue: max` にする。既定だと待ちを1本しか持てず、新しい起動が待っている起動を取り消すため。
- **先頭に来たら**:
  1. PR が最新の main を含んでいなければ、最新の main を取り込む(Update branch)。
  2. アプリに触らない変更(スクリプト・文書だけ)なら、macOS を使わず Linux のテスト(`scripts/agent/tests`、`scripts/ci` の単体テスト、actionlint)だけで検証する。
  3. 検証のワークフローに触る PR(`ios.yml`、キューのワークフロー、`devbox.yml` は除く)は、PR の定義で macOS の検証を1回流す。main の定義だけで流すと、検証を壊す変更が検証されずに main に入り、次からキューが全部赤になって、直す PR もマージできなくなるため。
  4. UI だけの変更(差分が描画のファイルだけ。main の版の `cosmetic.py` の `ALLOWED`)なら、Release archive と、シミュレータ向けのビルド(前後比較の「前」に使う)だけを確かめる。会話のスクロールと固まり、オンボーディング、課金に関わる画面は、UI だけの変更でも通常の検証にする。この経路で入った変更は、TestFlight に出す前に実機で確かめる。
  5. それ以外は、main の定義で `build-for-testing` → 単体テスト → 関係する UI テストを流し、並行して Release archive を1回流す。
  6. 同じコミットがすでにキューで緑になっていて、そのコミットが今の main を含むなら、流し直さない。
- **ビルドの再利用**: ビルド成果物を「tree の SHA＋Xcode の版」の名前で Artifact に置く(保存14日)。マージの方法は `merge` だけなので、マージ後の main のコミットの SHA は検証したコミットと違うが、tree の SHA は同じになる。UI テストが多い時は2台に配って半分ずつ流す(シャーディング)。ランナー側の失敗で流し直す時は、ビルドを省いて `test-without-building` で流す。
- **緑**: キューが `Struis / verify` を書く。必須のステータスチェックが揃った時点で、GitHub の自動マージが、ボタンを押した持ち主の名前でマージする。マージは持ち主の名前の push になるので、main への push で動くワークフローは普段どおり起動する。main が進んだのを見て、キューは次の PR へ進む。
  - 緑を書いてから10分たっても main が進まない(マージが失敗した)時は、Issue に理由を書いて次へ進む。
- **古い緑を残さない**: ルールセットの「最新の main を含むことを求める」(strict)は無効なので、古い main の上の緑はマージできてしまう。main が進むたびに、キューは、他の開いている PR の先頭のコミットにある緑の `Struis / verify` を pending に書き直す。
- **マージするのは GitHub**: キューも Claude もマージの API は呼ばない。Claude の環境ではマージの API が止められる(2026-11-06・07 に確認)。
- **強制の範囲**: `Struis / verify` はキューだけが書く決まり。ルールセットが強制しているのは「`Struis / verify` が緑でないとマージできない」ことだけで、誰が書いたかは見ていない(必須チェックに書き手の指定が無い。`statuses: write` を持つジョブや、持ち主の名前で動く Claude の環境も書ける)。キュー以外のジョブに `statuses: write` を持たせない。
- **赤か衝突**: キューから外し、Issue に理由を書く。自動マージは有効のまま残す。Claude が直して push したら、そのままキューの最後に並び直す。持ち主が押し直す必要は無い。UI テストが落ちた時は、失敗した瞬間のスクショと、そのテストの区間の録画を残す。直すのは Claude。
- **Update branch が拒否された時**: main に入った変更が `.github/workflows/` に触っていると、GITHUB_TOKEN による Update branch が拒否される可能性がある(未検証)。拒否されたら Issue に書き、Claude が次に起きた時に持ち主の名前で main を取り込んで push する。
- **push の禁止**: キューの先頭で検証中の PR のブランチには push しない。
- **作り**: Linux のジョブで、起動のたびに1段進めて終わる。待っている間ランナーを握らない。
- **非常口**: キューのワークフロー自体が壊れて直す PR も通らない時のために、持ち主をルールセットの例外(bypass)に入れるかは、持ち主の判断(「12. 持ち主の操作」)。

## 8. スクショと動画
- **撮る場所**: 開発中は Dev Box で撮る(`$DEVBOX_FILES` に置けば手元に届く)。マージキューで UI テストが落ちた時は、キューが撮って Artifact に置く(保存14日)。
- **持ち主に見せる**: Claude が先に確かめてから、会話にファイルとして送る(SendUserFile)。
  - 変えた画面ごとに、最新の main と PR の前後比較の画像を送る(iPhone と iPad)。動きが変わる時は動画も送る。
  - 「前」のスクショは、キューが Artifact に置いた main のシミュレータ向けのビルドを、Dev Box のシミュレータに入れて撮る。Linux だけで検証した変更はビルドを作らないので、アプリに触った直近の main のコミットをさかのぼって、その tree の SHA で探す。
  - PR のコメントには、文字の要約だけを残す。
- **Claude の見方**: Claude は動画を再生できないので、ffmpeg でフレームを切り出して見る。一瞬のちらつきや動きの滑らかさの最終判断は持ち主がする。
- **撮り方**: 録画はアプリが開いてから始める。送る前に縮める。

## 9. 監視(スケジュール実行)
- **仕組み**: この会話に一回限りのスケジュール実行(`send_later`)を入れて、Claude を起こす。1分刻みで、最大1分ほど遅れる。起きた時に結果を見て、まだなら次を入れ直す。
- **間隔**: 終わる時刻の見当がつくもの(マージキューの検証)は、終わる頃に1回起きる。まだの時だけ2分間隔でポーリングし、回数に上限を付ける。夜中は1時間ごとにキューと PR を見回る。
- **使用量**: 起きるたびに Claude の作業が1回分発生するので、細かくしすぎない。
- **持ち主への通知**: 詰まった時と、自動マージを押してほしい PR がある時は、Claude がスマホにプッシュ通知を送る。
- **キューからの通知**: キューが止まった時と赤が出た時は、キューが Issue に書き込む。
- **GitHub の通知の限界**: GitHub の PR の購読は、ステータスチェックの変化では Claude を起こさないことがある。だから監視はスケジュール実行で行う。

## 10. 依存関係と並列化
- 依存の無い作業は待たずに並べて進める。
- 依存は GitHub の Issue の依存関係(Blocked by / Blocking)で表す(Claude の環境から REST で書ける。2026-11-07 に #92←#91 で確認)。後の作業は、ブロックしている Issue の作業ブランチの上で進め、その PR がマージされるまでキューで待つ。
- ブロックしている作業が詰まっても、後の作業はその作業ブランチの上で進め、詰まった1か所以外を終わらせる。

## 11. 作業の決まり
- 作業を段階に分けたら、着手する前に全部の段階を事前検証する。権限・機能・持ち主の手作業を、実際に呼んで確かめる。
- 持ち主の判断や操作が要る箇所は、作業を始める前にまとめて全部伝える。
- Issue に書く前提は、確かめたもの(いつ・どの手段で)と未検証のものを分けて書く。未検証のまま実装に入らない。
- 「できない」と書くのは、実際に試して通らなかった時だけ。何を試し、何に止められたかを書く。
- 詰まったら、すぐ持ち主に知らせる。依存しない作業は進める。
- 作業の途中で関係のない問題を見つけたら、直さずに報告し、別の Issue にする。
- 1つの Issue で変える機能は1つ。UI だけの変更と、データや処理に触れる変更は Issue を分ける。

## 12. 持ち主の操作(これで全部)
- 最初に1回だけ: リポジトリの設定(Settings → General → Pull Requests)で「Allow auto-merge」を有効にする。2026-11-07 時点で無効。Claude が API(`PATCH /repos`)で有効にしようとしたが、安全確認に「共有の設定の変更」として止められた。マージキューの PR が main に入った後に有効にすれば足りる。
- キューができるまでの PR(Dev Box の PR と、マージキューの PR)のマージ。キューがまだ無いので、持ち主の手でマージしてもらう。
- PR ごと: 「Enable auto-merge」を押す(マージの許可)。
- 決めること: 非常口として、持ち主をルールセットの例外(bypass)に入れるか。入れるなら、ルールセットの変更は持ち主の操作(Claude の環境ではルールセットを変えられない)。

## 13. Claude の環境の制約(試した結果)
- **マージ**: PR のマージの API は、安全確認に「レビューなしのマージ」として止められる。持ち主の許可があっても止まる(2026-11-06、2026-11-07 に #88 で再確認)。
- **リポジトリの設定**: `PATCH /repos`(Allow auto-merge)は、安全確認に「共有の設定の変更」として止められる(2026-11-07)。
- **名義**: Claude の環境は GitHub で `DigiLog-lab`(持ち主のアカウント)を名乗る。Claude が作る PR・コメント・push は持ち主の名前になる。commit の作者は `claude`。
- **ルールセット**: 作成・変更は、通信の中継に書き込みを拒否される。読み取りはできる。
- **ブランチ保護**: 読み取りも「Resource not accessible by integration」で通らない。
- **Actions**: 実行・ジョブ・ログ・Artifact の読み取りはできる。キャッシュ、ランナー(`/actions/runners`)、変数(`/actions/variables`)の API は、通信の中継に拒否される(2026-11-07)。
- **GraphQL**: 拒否されるので REST を使う。
- **iOS 向けのビルド**: Claude の環境ではできない。だから Dev Box を使う。
- **できること**: clone と push(`.github/workflows/` の変更も含む)、Issue・PR・コメント・ラベル、Issue の依存関係の読み書き、`repository_dispatch` の送信、Actions の実行とログの読み取り、Artifact のダウンロード、ffmpeg、持ち主へのファイル送信(SendUserFile)、プッシュ通知。

## 16. 残る弱点
- Dev Box は、Claude が考えている間もランナーを1台握る。握るのは Claude が作業している間だけで、待っている間はアイドルタイムアウトで返す。
- Dev Box を使えるのは Claude が動いている間だけ。夜中はスケジュール実行で起きた時にまとめて回す。
- マージキューは1本ずつしか通らない。
- 2本の PR が合わさった時の不具合が、選ばれなかった画面で出ると見逃す。
- Actions のキャッシュの使用量が Claude の環境から見えない。
- 自動マージが押されていない PR は、持ち主が押すまで止まる。
- `Struis / verify` を書けるのがキューだけであることは、決まりで守っていて、ルールセットでは強制していない。

## 17. 実装の段取り
1. PR その1(#91): Dev Box とリモート実行(`mac` コマンド)、この仕様。以降の作業をこれで進めるので最初に作る。
2. PR その2(#92): テストの選び方、マージキュー、古い流れ(`refresh` の再検証、PR ごとの `Struis / verify`、エージェントの手元検証→ready→検証)の撤去。撤去と同時に、開いている PR の先頭のコミットの緑の `Struis / verify` を pending に書き直す。
3. 持ち主が Allow auto-merge を有効にした後、文書だけの害のない PR で自動マージの流れを確かめる。

## 18. 用語
| 言葉 | 意味 |
|---|---|
| Dev Box | Claude がコードを書いている間ずっと使う macOS ランナーのジョブ。Claude のリモート開発環境 |
| リモート実行(`mac` コマンド) | Claude の環境から Dev Box に命令を出し、結果を受け取るコマンド(`scripts/devbox/mac.py`) |
| マージキュー | 自前のマージキュー。main に入る前の唯一のゲート |
| `Struis / verify` | main へのマージに必須のステータスチェック。キューだけが書く決まり |
| 自動マージ(auto-merge) | GitHub 標準の機能。PR で「Enable auto-merge」を押しておくと、必須のステータスチェックが揃った時点で GitHub がマージする。持ち主がこれを押すことがマージの許可 |
| Blocked by | GitHub の Issue の依存関係。後の作業はブロックしている作業の後にマージする |
| 事前検証(preflight check) | 着手の前に、全部の段階を実際に試して、権限・機能・持ち主の手作業を確かめること |
| Issue エージェント | `agent` ラベルの Issue へのコメントで、macOS ランナー上の Claude Code が動く既存の仕組み。原則使わない |
