# Struis CI夜間実験の結論 — 2026-10-22

**平均10分でマージ判定が揃う構成は、今回の実験では達成できなかった。** 現在のRunnerで採用根拠があるのは、Simulator 1台、明示的な返事完了制御、練習問題の準備fixtureを使う構成。2台を同じVMで動かす案は、複製失敗とUI失敗が残り、採用しない。

10分を目指す次の中心は、成功済みの同じ入力の検証を再利用し、変更した機能のテストだけを実行できる構造にすること。今回、そのうち**保守的な結果再利用の判定処理を試作して実データで検証した**。機能ごとの依存グラフとSwiftターゲット分割はまだ実装していない。

## 並列案を採用しない根拠

最初の2worker試行2回は、iPhoneの複製時に不足しているwatchOSランタイムを参照し、対象56件を開始できなかった。最初の修正では存在しない `unpair_all` を使う実験コードの誤りがあり、2ジョブがビルド前に失敗した。いずれも記録を残している。

実際のペアUUIDを個別解除し、利用できないデバイスを除いた後、ビルド前の直接clone確認は2/2成功。しかしXcodeの並列試験では、片方は再びwatchOSの複製エラー、片方は2つのcloneで全件を開始して以下が失敗した。

- `ImmersionSceneChatUITests/testExploreRequiresManipulationThenFullCycleCompletes`: exploreのスライダーが出ない。
- `ImmersionSceneChatUITests/testJourneyWalkthroughForRecording`: XCTAssertTrue失敗。

CPU・メモリ不足が原因と確定したわけではない。このVM構成での速度・安定性の改善を示す結果は得られなかった。assertionを弱めたり、通るまで再実行したりしていない。

## 日常CIの具体案

まず、今回成功した1台構成と待機・fixture改善を通常テスト向けに整理する。fixtureで省いた例題生成〜練習開始の導線は専用のUIテストで残す。実験用のモード注入テストは環境変数必須なので、実験ブランチ全体をそのまま通常CIへマージしない。

次に、必要なテストを一件ずつ「今回実行して成功した結果」か「依存入力と実行条件が一致する以前の成功結果」で満たす判定を作る。結果がない・古い・失敗・対象欠落・未知の依存関係なら再実行し、対象一覧を黙って減らさない。上記の試作は、その全体入力版の判定まで。

機能ごとに狭める段階では、次の分割を先に行う。

| 分割先（提案・未実装） | 現在の主な対象 | 確かめる内容 |
|---|---|---|
| LedgerとEngineのSwiftターゲット | `strius/Ledger/**`、`strius/Engine/**` | 保存、採点、段階遷移、返事の処理。既存Unitを中心に実行 |
| 会話画面のターゲットと専用テストアプリ | `strius/Features/Chat/**` と必要なState | 入力、画像送信、スクロール、返事の記録中の操作 |
| 問題集画面のターゲットと専用テストアプリ | `strius/Features/Workbook/**` と必要なState | 撮影、結果表示、段階遷移の画面動作 |
| 実アプリ全体の短い結合確認 | Appの組み立てと画面遷移 | 各機能を実アプリへ組み込んだ時の接続 |

`WorkbookRules.swift` はFoundationとGRDB、`ChatTurns.swift` とLedgerはGRDB・OSLogに依存する。単純な「Foundationだけの純粋ロジック」として移せるわけではない。まずLedgerとEngineをまとめて境界を作り、外側のStateやDTOへの参照をコンパイルで確認する。

UIテストがすべて「全機能を含む同じアプリ」を起動したままでは、ビルドの依存グラフは全機能へ広がる。Swiftファイルを別フォルダへ置くだけでは選択範囲は狭まらない。専用テストアプリは、その画面と実際に必要な依存だけを組み込む小さなアプリで、画面固有の試験を受け持つ。実アプリの組み立て確認も別に残す。

そのうえで各テスト対象の識別値に、ターゲットの全ソース、依存ターゲットの識別値、テスト・fixture、ビルド設定、SDK・Simulator、実行条件を含める。例えば会話のスクロール試験は実際に問題集の画面から会話を開くため、会話機能だけでなくその導線も依存に含める。共通Engineや起動部分の変更では広い範囲を再実行する。

現時点で全UIの直列実行を維持したまま10分へ届く実測はない。次の受入条件は、代表的な変更でこの構成を実際に動かし、起動要求〜全必要結果が揃うまでの平均が600秒以内かを測ること。キャッシュ命中だけでなく、依存変更による再実行も含めて評価する。
