# struis-ios CI cost experiment — 2026-10-21

5本の既存UIテストについて、モックの固定待機を明示的な完了通知へ変え、繰り返しの練習問題準備を実際の状態遷移によるfixtureで置き換えた。テスト対象の確認処理を保ったまま、xcodebuildコマンドの平均実行時間は **366.20秒 → 245.70秒、120.49秒（32.9%）短縮**した。20回のUI実行はすべて成功。

これは5本の比較であり、CI全体やXcode Cloudとの速度差ではない。依存グラフによるテスト選択・モジュール分割は今回実装も測定もしていない。

## 変更内容と確認範囲

1. ReplyTail: 本文が見えた後の記録処理を、40秒・15秒等の固定待機だけに依存させず、UI確認後のDarwin notificationで解放する。質問が待機列に入り、前の返事が停止せず、次の返事が完了することを確認する。準備OKの返事の記録中に「先に進む」を押せることも確認する。
2. SplitGrading: 共通の例題生成・撮影・採点・練習問題準備を毎回UIで行う代わりに、実際のWorkbookMachine操作で練習問題5問の状態を作る。その後の対象操作と確認は既存のまま。fixture専用Unitテストも成功。
3. 各起動のUUIDで通知名を分離。対象の記録処理が解放されない場合は180秒で失敗する。単に既存タイムアウトを短くして高速化したものではない。

fixtureを使う3ケースでは準備導線そのものを通さなくなるため、この比較だけで全導線の品質担保を主張しない。全面採用時は準備導線を独立したテストで残す設計が必要。実験用モード注入テストは環境変数必須なので、このブランチ全体を通常CIへそのままマージしない。

## 判断

固定待機の同期化と共通準備のfixture化は、この5件では短縮の根拠が得られた。Runner変更や起動並行化だけで30分近いCI全体を解決できるという根拠はない。次の実装では、成功した変更を通常テストに適した形へ整理し、準備導線の専用確認を残したうえで、全UI suiteの時間と失敗率を測る。依存グラフ・モジュール単位の選択は別の段階として評価する。

通常CI、main、PR #39のheadは変更していない。実験の再現はこのブランチの `.github/workflows/ci-test-cost-experiment.yml` と `scripts/ci/benchmark_ui_cost.py` による。
